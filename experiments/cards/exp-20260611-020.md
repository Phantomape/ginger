## Post-Run Reflection

- Why did the result happen? All 36 existing closed forward rows across 8 sleeves
  already carried ticker, entry/exit dates, and pnl, and the broad OHLCV warehouse
  covers SPY/QQQ for every holding window, so read-side comparator enrichment
  repaired the `replacement_value_rows_present` activation blocker without touching
  sleeve decision logic. 27/36 rows enriched fully; 9 rows carry weekend/holiday
  entry dates (a pre-existing sleeve data quirk, mostly same-day low_deployment_etf
  rows) and are correctly flagged `missing_comparator_bars` instead of being
  silently priced.
- Which near-neighbor retry is now forbidden? Re-running a generic forward-readiness
  audit just to read these new fields. The next readiness audit should run only after
  materially more closed forward rows accumulate, and must use cost-adjusted
  replacement value (not raw pnl) as activation evidence.
- What new evidence would justify a retry? More closed forward rows per sleeve
  (min_closed_trades gates remain unmet) and daily-state wiring for accepted helpers
  that still lack `data/paper_sleeves` state directories.
