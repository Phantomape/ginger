## Post-Run Reflection

- Why did the result happen? `data_paths.atomic_write_text` used a bare `os.replace` for the final rename. On Windows that intermittently raises `PermissionError` (transient AV/search-indexer/concurrent-reader lock); the daily pipeline swallows per-step write failures, so the artifact silently ended up as an orphan `.<name>.<rand>.tmp` with no final file. quant_signals_20260627 and bracket_orders_20260627 were the latest victims (5 earlier days hand-recovered in exp-20260626-005; backtester hit the same class in exp-20260627-021). Adding bounded `os.replace` retry (parity with `backtester._atomic_write_json`) + a recover-before-delete daily orphan sweep wired into run.py startup fixes it durably. Verified: 18/18 unit checks; recovery promoted 2 missing finals, cleaned 17 stale temps, matcher records for 06-27 went 60→66, recovered orders file benign (0 resting/stop/exit).
- Which near-neighbor retry is now forbidden? Do not add another one-shot manual orphan-recovery experiment (the exp-005 pattern) — recovery + cleanup is now automatic under the run lock. Do not "fix" this by widening the generic `stale_artifact_sweep` to delete daily-signal temps (that would destroy recoverable data; daily dirs use recover-before-delete).
- What new evidence would justify a retry? Only a NEW persistence failure signature not covered by the retry/recovery (e.g. final exists but is truncated, or a non-PermissionError rename failure), or a different artifact dir that needs adding to `_RECOVERABLE_DIRS`.
